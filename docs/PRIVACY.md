# Invoice file privacy

SANAD encrypts exported agreement files using **AES-256-GCM**. Every export creates an independent cryptographically random 256-bit key and 96-bit nonce. The ciphertext includes a 128-bit authentication tag. The record type, format version and algorithm identifier are authenticated as additional data. The file parser accepts only the five defined fields, canonical base64, the expected nonce/tag dimensions and records up to 1,000,000 UTF-8 bytes.

The browser uses WebCrypto. Expo uses the installed Expo Crypto native AES-GCM API, independently of the existing ECDSA compatibility shim. Both use the same envelope format. The key is returned separately as 43 base64url characters and is never included in the envelope. The UI must keep it in current-session memory, export the encrypted file, and let the user deliver the key separately to the intended recipient. Anyone with both can read the file. There is no forgotten-key recovery.

The business invoice signature layer uses canonical JSON, SHA-256 and ECDSA P-256. Importing decrypted content still calls `parseInvoiceRecord`; decryption alone does not establish a valid invoice. The signed object includes the network, USDC mint and recipient wallet. The customer also acknowledges the issuer's exact signature; imports pin records against previously saved copies. These signatures detect changes and bind consent to particular content and included signing keys. They do not independently authenticate the person's name or business identity. Browser signing keys are non-extractable; the Expo shim keeps private key bytes in a WeakMap. Neither is a claim of hardware-backed key storage.

This feature protects the contents of shared encrypted files. It does **not** encrypt the whole app, its local storage, clipboard, notifications, or blockchain transactions. Solana addresses, token amounts and transaction history remain public. Invoice text and customer information should remain off-chain. The scheme has no authenticated key exchange, forward secrecy, secure device enrollment or account recovery and should not be described as an end-to-end encrypted messaging protocol.

Verification: `tests/envelope.test.ts` covers Unicode round trips, key/nonce freshness, absent plaintext/key in exports, wrong keys, modified nonce/ciphertext/tag, altered metadata, strict bounds, independent Node AES-GCM interoperability in both directions, authenticated metadata, and Hermes UTF-8 fallback decoding. Native Expo adapter typing is checked separately. Actual encryption on physical Expo devices still requires the two-phone acceptance test.
